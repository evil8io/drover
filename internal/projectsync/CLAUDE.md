# project-sync

The human document of this component is `docs/project-sync.md`. Update it together with a behaviour change.

- Rancher sets `field.cattle.io/projectId` on a new namespace about 3 s after the namespace is created. Act on `MODIFIED` as well as on `ADDED`. Otherwise, the keys of a new namespace are missing until the next reconcile run.
- Read the project of a namespace from the annotation `field.cattle.io/projectId`. Never read it from the label. Rancher sets the label from the annotation, but it keeps the label when the annotation is removed. Rancher grants the project roles by the annotation. The label stays when kubectl removes the annotation, and when a project is deleted.
- When a user moves a namespace to "no project" in the Rancher UI, Rancher removes the label and the annotation in one write. The namespace then no longer matches the label selector of the watch, so the watch gets a DELETED event. After that, only a reconcile run finds the namespace, with a list that has no selector. That DELETED event has the object from before the change (verified on Kubernetes 1.35). So read the namespace again before you act on it. Drop the event when the read fails, because its object names the project that the namespace left.
- project-sync takes the cluster set from `GET /v3/projects`, which Rancher filters by RBAC. Do not add a cluster list call. A cluster without a visible project has nothing to sync.
- Remove from every decoded namespace each key that project-sync does not read. A tenant controls the size of its namespace metadata, and the pod has a fixed memory limit.
- Put the byte limit of a list on each item, not on the page. A tenant controls the size and the count of its namespaces, so a page limit lets one tenant stop the list of the whole cluster.
- Treat a value of the ownership record above `maxRecordValue` (4096 bytes) as absent. A tenant can fill a record up to the 256 KiB annotation limit, and a record that project-sync writes is a short key list. Reject in `New` a key set whose own record is longer. The prune drops such a record, and project-sync then never removes a key of it.
- The worker and the lister read the token file per queue item, because the token changes at a rotation while the stream stays open.
- Restart a watch stream without a resource version only on a 410, as the status of the answer or as the code of an `ERROR` event. After another `ERROR` event, keep the resource version, because a start without one sends an `ADDED` event for every namespace again.
- The ownership record is the two namespace annotations `drover-managed-labels` and `drover-managed-annotations`. The two annotations have bare keys, without a prefix, on purpose. A tenant can edit the two annotations. So project-sync removes only a key that the flags name, and it ignores every other key in the record. In its flags, project-sync rejects the two record keys.
- The name path, which writes the display name, has priority on its key. Write the display name to a key that is in `--labels` and in `--name-label` at once. Never write the label of the Project object to that key.
- A display name is free text, so the sanitised label is lossy and not unique. The value of the annotation is the raw name.
- When a patch gets 404, 409, or a 403 whose message names the terminating state, project-sync skips the patch and counts no error. The next reconcile run repeats the work.
- After an upgrade with a new record key, the first reconcile run patches every namespace once. Expect one patch per namespace in the metrics after such a release.
- A deployment tool that reads back every label of a namespace shows the keys of project-sync as drift. Name a new key in `docs/project-sync.md`, so that a deployer can ignore it.
- The project watch reads `GET /k8s/clusters/local/apis/management.cattle.io/v3/projects?watch=true` (verified against Rancher 2.14.5). Grant the cluster-wide `list` and `watch` on `projects` with a `ClusterRoleTemplateBinding` on the `local` cluster. A per-cluster binding does not give this permission.
- Start the project watch in the reconcile run, after the first snapshot. Before that, the watch has no snapshot to compare against. Also, the watch would log a warning per attempt when the token file is missing.
- Expect one `ADDED` event per Project after a restart without a resource version. For each such event, project-sync compares the Project in memory, so a restart costs no request.
- Never let the project watch start a reconcile run. A cluster member can create Projects, so a trigger in the project watch would let that member start runs at any time.
- Take a token from the cluster limiter before each request of the worker and the lister, not per queue item. A project owner can edit its Project in a loop, and one project event sends 4 requests, or 9 with OpenBao, when every object exists. A start of the watch without a resource version puts every namespace on the queue, and most of them need no request.
- Replace the snapshot maps of a cluster on every change. Never mutate them in place, because a worker and the reconcile run read them without a lock.
- A reconcile run that reads the project list before a Project change can overwrite that change in the snapshot. It can then patch the old values back. This gap is known and accepted, because the time window lasts one list request, and the next event or run ends it.

## Service accounts

The facts in this section are verified live against Rancher 2.14.5, and against the source of Rancher 2.14.6 and its webhook 0.10.12.

project-sync puts the ServiceAccounts of each tenant project in an account namespace. The account namespaces of a cluster are in its account project.

- Trust an account project only by the label `drover-service-accounts` together with the annotation `field.cattle.io/creatorId` equal to the service user. A project owner can set the label on its own project. On an update, the webhook denies a request that changes or adds the creator annotation, also from an admin. A cluster member can create a project with the service user as creator, because no webhook compares the annotation with the requester. But Rancher then binds only the service user as owner, so that member gets no role in the project.
- Create the account project without `field.cattle.io/no-creator-rbac`. The webhook rejects that annotation together with a creator, and the trust check rejects a project without a creator.
- Use an account namespace only in an account project. The name is not proof, because a tenant can create a namespace with that name first in its own project.
- Move a namespace in no project into the account project, or delete it in the sweep, only when a ClusterRoleBinding of project-sync names it as owner. The binding must name the namespace by uid. The namespace webhook checks `manage-namespaces` on the new project only. It checks nothing when a request removes the project annotation. So a project owner can put its own namespace, with its own RoleBindings, into no project.
- Do not set `field.cattle.io/creatorId` on an account namespace. Rancher deletes a namespace with that annotation together with its project. The ServiceAccounts of that namespace are then deleted too, and every token of those ServiceAccounts becomes invalid. Without the annotation, the namespaces of a deleted account project remain in no project. The next reconcile run moves them into a new account project.
- Delete an account namespace of an unknown project only after Rancher answers `GET /v3/projects/<cluster>:<project>` with 404. Keep the namespace on any other status. The project list of a reconcile run can be older than a new project.
- Delete the bindings of a project before you delete its account namespace. Keep the namespace when a binding delete fails. A binding names a ServiceAccount by namespace and name, not by uid. So a binding that remains after the namespace is deleted grants its rights to the next tenant who creates that namespace name.
- Put the uid of the namespace into the key of the worker cache. A CI job can delete a namespace and create it again within one interval, and the queue can merge the `DELETED` item into the next `ADDED` item.
- When the new project of a moved namespace has no trusted account namespace yet, delete the RoleBindings of the old project at once. Otherwise, the ServiceAccounts of the old project keep their rights in a namespace of another project until the next reconcile run.
- Never set `blockOwnerDeletion` on an owner reference. It needs a right on the owner that the service user does not have.
- Rancher creates `<project>-namespaces-edit` and `<project>-namespaces-readonly` shortly after the project is created, also when the project has no member and no namespace.
- Send a PATCH as `application/merge-patch+json`. The API server answers 415 to `application/json`.

## OpenBao

The facts about the answer to a missing mount are from the source of OpenBao 2.7.0. The facts about mounts, roles, policies, and ACLs are from OpenBao 2.6.3. No part of this section is checked live yet.

- project-sync writes every OpenBao object that it derives from a Rancher object. These objects are the mounts, their config, the roles, and the ACL policies. Do not move this work back to an operator. Because of the token refresh, project-sync already writes to OpenBao. The operator added a delay to each new project. It did not correct drift, and an uninstall hung.

- Refresh the config of a cluster when less than half of the lifetime of its token remains. OpenBao keeps a written `service_account_jwt` and never renews it, and EKS limits a TokenRequest to 24 h. The other half is the time for the retries of a failed write.
- Take the expiry from `status.expirationTimestamp` of the TokenRequest answer. Never take it from `--openbao-token-ttl`. The API server can shorten the lifetime.
- Compare the uid of the ServiceAccount `openbao` with the uid of the last write. With a new ServiceAccount, the written token is invalid. With the expiry check alone, project-sync would wait up to half of the lifetime.
- Write the config after project-sync creates the mount. Also read `<mount>/config` at most once per 10 minutes, and write the config again after a 404 or a changed field. The expiry in memory does not show a mount that an admin disabled, or an OpenBao that lost its storage. OpenBao answers the read of a mount without config with 404 and an empty error list (`sdk/logical/response_util.go`). The read never returns `service_account_jwt` (`builtin/logical/kubernetes/path_config.go`). So an older token from a restored backup stays until another condition of the write is true.
- Send the Rancher CA as `kubernetes_ca_cert` in every write, also when it is empty. The Kubernetes secrets engine of OpenBao cannot skip the TLS verification. When `kubernetes_ca_cert` has a value, the engine trusts only that CA. Otherwise, it trusts the system roots. OpenBao removes the stored CA on an empty string in the request, because it writes every field that the request has. The sources are `builtin/logical/kubernetes/client.go` and `path_config.go` of OpenBao 2.6.3.
- Read the setting `cacerts` in every run that has a cluster to keep. Read it also in a run without a due token, so that OpenBao gets a rotated CA in one run. Write nothing after a failed read. With an empty CA, OpenBao verifies a private certificate with the system roots. Every token request of the engine then fails.
- The service user reads `/v3/settings/cacerts` through the GlobalRole `user-base`, which grants `get` on `settings` (Rancher 2.14.6, `pkg/data/management/role_data.go`).
- Keep `--openbao-rancher-url` separate from `--rancher-url`. Through the Rancher Service, project-sync can reach Rancher with `--rancher-insecure-skip-verify`, but OpenBao verifies the certificate of Rancher.
- OpenBao checks the policy before it routes a request. OpenBao answers a write under a missing mount with 404 `no handler for route "<path>". route entry not found.` only when the policy allows `update` on the path. Otherwise, OpenBao answers 403. An older Vault server answers 400 with the same message. The sources are `internal/vault/routing/router.go` and `sdk/logical/response_util.go`.
- Use `drover-openbao` only in an account project. Move it out of no project only with the proof of an OpenBao RoleBinding in a trusted account namespace. Only project-sync and an admin write there. Never take a binding in another namespace as proof. A tenant can write a binding with that owner reference in its own namespace.
- The RoleBinding `drover-openbao` names `drover-openbao/openbao` by namespace and name. Let the namespace `drover-openbao` own it by uid. Delete every such RoleBinding when the namespace is not trusted. Otherwise, a tenant who creates `drover-openbao` and a ServiceAccount `openbao` gets the tokens of every project role.
- The lister writes the OpenBao Role and RoleBinding of a project with the uid of `drover-openbao` that the last reconcile run trusted. Keep that uid only after a check that trusts the namespace. Clear the uid on every other result. Otherwise, the RoleBinding would name the ServiceAccount of a namespace that project-sync does not own. The lister creates each object first and reads it only after a 409, so it needs no list call. Before the write, read `drover-openbao` in the lister. Write only when its uid and its project are still the trusted ones. A tenant can delete the namespace and create it again in its own project within one interval.
- For a missing mount, OpenBao answers `GET sys/mounts/<path>` with 400 `No secret engine mount at <path>/` (`vault/logical_system.go`, `handleReadMount`). That read also matches a parent mount, so check the `type` of the answer.
- `sys/mounts`, `sys/mounts/*`, and `sys/policies/acl/*` are not root paths, so the policy of project-sync needs no `sudo` (`vault/logical_system.go`, `PathsSpecial.Root`). OpenBao adds a slash to the end of the path of a LIST request (`http/logical.go`). The ACL matches the path without the slash only when no rule matches the path with it (`vault/policy/acl.go`). So put `list` on `kubernetes/+/roles/*`, because that pattern matches `kubernetes/<cluster>/roles/`. A rule on `kubernetes/+/roles` alone gave 403 on OpenBao 2.6.3. `list` on `sys/policies/acl` is enough, because `sys/policies/acl/kubernetes-*` does not match `sys/policies/acl/`.
- On a role write, OpenBao keeps every field that the request does not send (`builtin/logical/kubernetes/path_roles.go`). Send every field that can give a credential more rights, also when the field is empty. Otherwise, OpenBao keeps the change in a changed role. Only one of `service_account_name`, `kubernetes_role_name`, and `generated_role_rules` can have a value.
- Find the roles to delete from the role names in the mount of a cluster. Find the policies to delete from their names too, because a policy without a role has no role name. A cluster id and a project name both have dashes. So split a policy name only at a cluster id of the run. Take the longest cluster id that fits.
- Do not change the separator of the policy name. A Rancher cluster id is `local`, `c-` and five characters, or `c-m-` and eight characters. A project name is `p-` and five characters, and the role names are a fixed set. So the split at the longest cluster id finds one pair for each name that project-sync writes. A new separator renames every policy that exists, and every client that names a policy then fails.
- Read a policy before you delete it. Delete it only when its text is the text that project-sync writes for the parsed cluster, project, and role. A text without `allowed_parameters` also counts, because earlier releases wrote that text. The name does not prove the writer. A policy `kubernetes-c-1-grafana-read-only` of an operator parses as the project `grafana` of `c-1`, and Rancher answers 404 for that project. Accept only a project part that is a label value, because it goes into the path of a Rancher request.
- Do not delete a policy of a cluster outside the run, unless Rancher answers 404 for that cluster. Its name can start with the id of a cluster of the run. The text compare keeps such a policy, because the path in the text has a slash after the cluster id. Delete the policies before you delete the roles, so that the role stays as the key for a retry.
- Delete the mount of a cluster outside the run only after `GET /k8s/clusters/local/apis/management.cattle.io/v3/clusters/<id>` answers 404. Also require the Rancher URL of that cluster in the config of the mount. The Kubernetes API checks the right before it looks for the object, so a missing right gives 403, never 404. A mount without that config can belong to another writer. Delete the policies of the cluster first, so that the mount stays as the key for a retry. The delete of the mount also deletes its roles and its config.
- Restrict the parameters of `creds/<role>` in the policy to `kubernetes_namespace` and `ttl`. The endpoint also accepts `audiences` and `cluster_role_binding` (`builtin/logical/kubernetes/path_creds.go`). A token with another audience is valid for other services than the API server, for example the OIDC federation of a cloud provider.
- Read a role or a policy that the run keeps at most once per 10 minutes. Each reconcile run finds a missing object with its list, so the read finds only a changed object. The project watch writes without a read, and it skips an object that project-sync read or wrote in those 10 minutes.
- Keep the client token until a fifth of its lifetime remains. OpenBao can give batch tokens for a login role, for example with a lifetime of 5 minutes. A batch token cannot be renewed.
- After a 403, log in again at most once per reconcile run. The project watch uses the same limit. A second 403 in the run is a missing right, and another login gets the same rights.
- Skip `drover-openbao` in the sweep of the account namespaces. It has the account prefix and no project, so the sweep deletes it after its 404 check. A project called `openbao` gets no accounts, because the name of its account namespace is also `drover-openbao`.
- Keep the `resourceNames` of the Role inside the `serviceaccounts/token` grant of the service user. The user creates and binds the Role without `escalate` and `bind`, because the user has every rule of the Role.
- OpenBao reaches a cluster through the Rancher proxy with a ServiceAccount token. For that, Rancher needs a `ClusterProxyConfig` per cluster. See `internal/filter/CLAUDE.md`.

## Login roles

`trust.go` has the rules, the parser of the trust annotation, and the format of the status annotation. `trust_roles.go` has the OpenBao writes and the status write. The integration tests of the private repository run a copy of `testdata/trust/` against the admission policy of the chart. Change a case in both places. No part of this section is checked live yet.

- Never log the value of the trust annotation or of the status annotation. A tenant writes the document, and its claims can contain the names of private repositories or accounts. Log the project, the index of a statement, a statement name that matches the name pattern, and the reason.
- Keep the four rules against a loop of status writes. After each status write, the project watch gets a `MODIFIED` event of the Project. When the code breaks one rule, the service writes the status again at every event.
  - Write the status only when it differs from the current value. Do not compare `observedAt`.
  - Set `observedAt` only at that write.
  - Keep each message a fixed text per reason. Never put the parser output or tenant text into a message.
  - Patch only the status key, with a merge patch.
- Exclude the status from the change compare of the project watch. Store the status in the snapshot. Otherwise, at the next event the service compares against an old status and writes the status again.
- Delete a role of the last status only when these conditions are true:
  - The mount of the role is a mount of the rules file.
  - The name of the role is `<project>-<valid statement name>`.
  - No other known project fits the name.

  A tenant can edit the status when the admission policy is off. Without these checks, the service deletes the role of another project when a tenant adds that role to the status.
- In the reconcile run, delete a role by its name only for a project that the run checked. The snapshot must also still have the trust value of that check. After the project list of the run, the project watch can get a project event with a new statement. Without the check of the trust value, the run deletes the role of the new statement. A login with that role then fails until the next run.
- Keep the role of a statement whose write failed. It is the last role that works.
- Write a role only when exactly one known project of all clusters fits its name. An auth mount is not per cluster, and Rancher keeps a project name unique per cluster only. When two projects fit one name, the service overwrites the role at every run, once for each project.
- Write a role again after the 10-minute window, without a read. The read answer of a JWT role has other value types than the write body, for example seconds for `token_ttl`. A compare then needs a conversion per field. Log a write with the body of the last write at the debug level. Do not count that write as a change, because it changes nothing.
- Keep the status at most `maxStatements` + 1 statements long. A document of 16384 bytes can have thousands of empty statements. A status with an entry per statement is then larger than the annotation limit of the API server.
- Reject a trust key in `--annotations` and `--name-annotation`, at the start and at each reload of the rules file. Otherwise the namespace sync copies the document to every namespace of the project.
- Take a token of the cluster limiter before each OpenBao request of the trust step in the event path. A project owner can edit the trust annotation in a loop.
