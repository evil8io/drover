# project-sync

The reference of this component is `.claude/docs/project-sync.md`. Read it first. Update it together with a behaviour change. Do not repeat its content here. `docs/project-sync.md` is the short document for users.

- Read the project of a namespace from the annotation `field.cattle.io/projectId`, because Rancher grants the project roles by the annotation. The label stays when kubectl removes the annotation, and when a project is deleted.
- When a user moves a namespace to "no project" in the Rancher UI, Rancher removes the label and the annotation in one write. The `DELETED` event of the watch then has the object from before the change (verified on Kubernetes 1.35). Its object contains the project that the namespace was removed from. So never act on it without a new read.
- Remove from every decoded namespace each key that project-sync does not read. A tenant controls the size of its namespace metadata. The pod has a fixed memory limit.
- Reject in `New` a key set whose own ownership record is longer than `maxRecordValue`. Such a record is dropped in the prune, and project-sync then never removes a key of it.
- The worker and the lister read the token file per queue item, because the token changes at a rotation while the stream stays open.
- After an `ERROR` event with a code other than 410, keep the resource version. When the watch starts without one, it gets an `ADDED` event for every namespace again.
- When a patch gets 404, 409, or a 403 whose message contains the terminating state, project-sync skips the patch and does not count an error.
- After an upgrade with a new record key, the first reconcile run patches every namespace once. Expect one patch per namespace in the metrics after such a release.
- A deployment tool that reads back every label of a namespace shows the keys of project-sync as drift. Name a new key in `docs/project-sync.md` and in `.claude/docs/project-sync.md`, so that a deployer can ignore it.
- Start the project watch in the reconcile run, after the first snapshot. Before that, the watch does not have a snapshot to compare against. Also, the watch would log a warning per attempt when the token file is missing.
- Never let the project watch start a reconcile run. A cluster member can create Projects, so with a trigger in the project watch, that member could start runs at any time.
- Store the trust status and the namespace count in the snapshot. Exclude both from the change compare of the project watch. After each write of one of them, the project watch gets a `MODIFIED` event of the Project. When the compare includes the value, each write starts the work of a project change. When the value is not in the snapshot, the service compares the next event against an old value, and it writes the value again.
- Do not write a namespace count for a cluster before the reconcile run lists its namespaces. A count from events alone does not include the namespaces without an event. With a wrong `"0"`, the admission policy of the chart allows the delete of a Project that still has namespaces.
- Keep the journal of the worker moves around the namespace list of the reconcile run. Keep it from `beginList` to `replace` or `endList`. Without it, a move during the list request is lost. After a lost move, project-sync can write a wrong `"0"`. With a wrong `"0"`, the delete of a Project that has a namespace is allowed.
- Hold the count write lock of the cluster from the compare to the store in the snapshot. Without it, the run and the worker compare against the same old value. The one that stores last then overwrites the newer count.
- Write the namespace count from the project watch when the count of an event differs from the sets. The project watch can lag behind the worker. When the stored value is from an old event, the worker does not do its next write. After each write, the project watch gets one event with the written value. That value is equal to the sets, so the correction does not loop.
- Never let a lister item replace a waiting item of the patch queue. Never count a lister item. The list of the lister can be older than a watch item of the same namespace. The worker then acts on a project that the namespace was removed from.
- Take a token from the cluster limiter before each request of the worker and the lister, not per queue item. A project owner can edit its Project in a loop. When the watch starts without a resource version, every namespace is put on the queue. Most of them do not need a request.
- Replace the snapshot maps of a cluster on every change. Never mutate them in place, because a worker and the reconcile run read them without a lock.
- A reconcile run that reads the project list before a Project change can overwrite that change in the snapshot. It can then patch the old values back. This gap is known and accepted, because the time window lasts one list request, and the next event or run ends it.

## Service accounts

The facts in this section are verified live against Rancher 2.14.5, and against the source of Rancher 2.14.6 and its webhook 0.10.12.

- Trust an account project only by the label `managed.drover.evil8.io/account-project` together with the annotation `field.cattle.io/creatorId` equal to the service user. A project owner can set the label on its own project. On an update, the webhook denies a request that changes or adds the creator annotation, also from an admin. A cluster member can create a project with the service user as creator, because the webhooks do not compare the annotation with the requester. But Rancher then binds only the service user as owner, so that member does not get a role in the project.
- Create the account project without `field.cattle.io/no-creator-rbac`. The webhook rejects that annotation together with a creator. The trust check rejects a project without a creator.
- Move a namespace in no project into the account project only when a ClusterRoleBinding of project-sync names it as owner by uid. The same rule applies to a delete in the sweep. The namespace webhook checks `manage-namespaces` on the new project only. It does not check a request that removes the project annotation. So a project owner can put its own namespace, with its own RoleBindings, into no project.
- Do not set `field.cattle.io/creatorId` on an account namespace. Rancher deletes a namespace with that annotation together with its project. The ServiceAccounts of that namespace are then deleted too, and every token of those ServiceAccounts becomes invalid.
- Put the uid of the namespace into the key of the worker cache. A CI job can delete a namespace and create it again within one interval. The queue can then merge the `DELETED` item into the next `ADDED` item.
- A namespace can be moved to a project that does not have a trusted account namespace yet. In that case, delete the RoleBindings of the old project at once. Otherwise, the ServiceAccounts of the old project keep their rights in a namespace of another project until the next reconcile run.
- Never set `blockOwnerDeletion` on an owner reference. It needs a right on the owner that the service user does not have.
- Rancher creates `<project>-namespaces-edit` and `<project>-namespaces-readonly` shortly after the project is created, also when the project does not have a member or a namespace.
- Send a PATCH as `application/merge-patch+json`. The API server answers 415 to `application/json`.
- In the sweep of the bound bindings, `ensureBoundRoles` deletes a RoleBinding in any namespace when two conditions are true. The name of the RoleBinding has the bound prefix of the project. Its labels are the labels of the service. A tenant can write such a binding in its own namespace, and the service then deletes it. This matches `managedRoleBinding`. The cost is one delete per such tenant write.

## OpenBao

The facts about the answer for a mount that does not exist are from the source of OpenBao 2.7.0. The facts about mounts, roles, policies, and ACLs are from OpenBao 2.6.3. On OpenBao 2.7.1, the mount create and the config write are checked live. The other facts of this section are not checked live.

- project-sync writes every OpenBao object that it derives from a Rancher object: the mounts, their config, the roles, and the ACL policies. Do not move this work back to an operator. The operator added a delay to each new project. It did not correct drift. An uninstall hung.
- Refresh the config of a cluster when less than half of the lifetime of its token remains. The other half is the time for the retries of a failed write.
- Read the setting `cacerts` also in a run without a due token. Then OpenBao gets a rotated CA in one run.
- Keep `--openbao-rancher-url` separate from `--rancher-url`. Through the Rancher Service, project-sync can reach Rancher with `--rancher-insecure-skip-verify`, but OpenBao verifies the certificate of Rancher.
- Never take an OpenBao RoleBinding outside a trusted account namespace as proof for `drover-openbao`. A tenant can write a binding with that owner reference in its own namespace.
- Delete every RoleBinding `drover-openbao` when the namespace `drover-openbao` is not trusted. Otherwise, a tenant who creates `drover-openbao` and a ServiceAccount `openbao` gets the tokens of every project role.
- Read `drover-openbao` in the lister before each write of the OpenBao Role and RoleBinding of a project. A tenant can delete the namespace and create it again in its own project within one interval. The lister creates each object first and reads it only after a 409, so it does not need a list call.
- Check the `type` in the answer of `GET sys/mounts/<path>`, because that read also matches a parent mount (`vault/logical_system.go`, `handleReadMount`).
- Put `list` on `kubernetes/+/roles/*`, not on `kubernetes/+/roles` alone. OpenBao adds a slash to the end of the path of a LIST request (`http/logical.go`). The ACL matches the path without the slash only when no rule matches the path with it (`vault/policy/acl.go`). With a rule on `kubernetes/+/roles` alone, OpenBao 2.6.3 answered 403.
- Only one of `service_account_name`, `kubernetes_role_name`, and `generated_role_rules` of a role can have a value.
- Do not change the separator of the policy name. A Rancher cluster id is `local`, `c-` and five characters, or `c-m-` and eight characters. A project name is `p-` and five characters. The role names are a fixed set. So for each name that project-sync writes, project-sync finds one pair when it splits the name at the longest cluster id. With a new separator, every policy that exists is renamed, and every client that names a policy then fails.
- The name of a policy is not a proof of its writer. For a policy `kubernetes-c-1-grafana-read-only` of an operator, project-sync parses the name as the project `grafana` of `c-1`. Accept only a project part that is a label value, because it is put into the path of a Rancher request.
- Delete the policies of a cluster or a project before its roles and its mount. The role or the mount then stays as the key for a retry.
- The Kubernetes API checks the right before it looks for the object. So without a right on `clusters`, the Kubernetes API answers 403, never 404, and the mount of that cluster stays.
- Keep the `allowed_parameters` of the `creds/<role>` policy at `kubernetes_namespace` and `ttl` (`credsParameters` in `openbao_roles.go`). The endpoint also accepts `audiences` and `cluster_role_binding` (`builtin/logical/kubernetes/path_creds.go`). A token with another audience is valid for other services than the API server, for example the OIDC federation of a cloud provider.
- Keep the client token until a fifth of its lifetime remains. OpenBao can give batch tokens for a login role, for example with a lifetime of 5 minutes. A batch token cannot be renewed.
- After a 403, log in again at most once per reconcile run. A second 403 in the run means that a right is absent. With another login, project-sync gets the same rights.

## Login roles

`trust.go` has the rules, the parser of the trust annotation, and the format of the status annotation. `trust_roles.go` has the OpenBao writes and the status write. The integration tests of the private repository run a copy of `testdata/trust/` against the admission policy of the chart. Change a case in both places.

- Never log the value of the trust annotation or of the status annotation. A tenant writes the document. Its claims can contain the names of private repositories or accounts.
- Keep the status rules of `.claude/docs/project-sync.md` against a loop of status writes. The rules are in the sections "The status annotation" and "Rules of the service". After each status write, the project watch gets a `MODIFIED` event of the Project. When the code is in conflict with one rule, the service writes the status again at every event.
- Do not change the separator `_` of a login role name. The name is `<cluster id>_<project>_<statement name>`. An auth mount is not per cluster, and a project name is unique only in its cluster, so the name needs the cluster id. A cluster id and a statement name do not contain a `_`. The service thus splits a name at the first and the last `_`. That split is the only one. A cluster id, a project name, and a statement name can each contain a dash. So a name with a dash as the separator has more than one split. The reconcile run keeps every listed role with another name form. `ownsLogin` also accepts the form `<project>_<statement name>` of earlier releases for the project itself, when the other clusters do not have a project with that name. The first trust step after the upgrade thus deletes each old role of the last status. A role of the old form that is not in a status stays in OpenBao. A login with such a role still works.
- A listed login role can belong to a project that neither the run nor the snapshot has. Read such a role before the reconcile run deletes it. Delete it only when its first token policy is a policy of the service. That policy must be for the cluster and the project of the name. An operator can write a role with a name of the same form, for example `c-1_infra_deploy` with the policy `admin`. The 404 of Rancher for `c-1:infra` is not a proof that the service wrote that role.
- Keep the conditions for the delete of a role of the last status, in `.claude/docs/project-sync.md`, "Rules of the service". A tenant can edit the status when the admission policy is off. Without these checks, the service deletes the role of another project when a tenant adds that role to the status.
- Read at most `maxStatements` + 1 entries of the last status. A tenant can write a status with thousands of entries. For each entry, the service can send a delete request and write a log line.
- In the trust step of the reconcile run, take each project from the snapshot. Do not take it from the project list of the run. After the project list, the project watch can store a narrower document. With the listed document, the run writes the role of a removed statement again.
- In the reconcile run, delete a role by its name only while the snapshot has the trust value that the run checked. After the project list, the project watch can get a project event with a new statement. Without this check, the run deletes the role of the new statement.
- Keep the role of a statement whose write failed. It is the last role that works.
- Write a login role again after the 10-minute window without a read. The read answer of a JWT role has other value types than the write body, for example seconds for `token_ttl`. A compare then needs a conversion per field.
- Keep `drover.sync.trust.statements.ready` an observable gauge whose callback reads the data points of each project from a map. With cumulative temporality, the OpenTelemetry SDK exports at each collection every attribute set that a synchronous gauge ever recorded. So the data point of a removed statement would stay in the export with its last value.
- Keep `gaugeCardinalityLimit` in `cmd/drover/project_sync.go` above the SDK default of 2000. The reason is that a tenant controls the count of data points of `drover.sync.trust.statements.ready`.
